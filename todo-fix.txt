2. IMAGES LOAD SLOWLY
================================================================================

Full plan: docs/image-loading-plan.md
Transfer-side fix (pre-generated sizes, WebP): docs/image-variants-plan.md

Root cause is the source assets, not the code: ~33 MB of PNG album covers on
production (one is 12.6 MB), five of which the dashboard carousel fetches to
draw at 90x90. Re-encoding them is worth 50-100x and needs no code - but it
needs production Storage access.

The code makes it worse in three ways:
  - 40 Image.network sites vs 2 CachedNetworkImage, so nothing caches to disk
    and every cold start re-downloads everything.
  - cacheWidth / memCacheWidth appear ZERO times, so every image decodes at
    full resolution regardless of the 90x90 box it lands in.
  - Flutter's in-memory cache holds DECODED bitmaps, so a few large photos
    evict each other mid-scroll.

Fix is one wrapper widget in lib/custom_code/, not 40 hand-edits - the decode
cap must be width x devicePixelRatio, which needs a BuildContext and so cannot
be a literal at each call site.

Note for anyone working from older copies of this file:
  - error handling: 4 sites in TWO files (music_player_widget.dart:189,:268 and
    community_widget.dart:599,:768), not "3, all in music_player_widget".
  - the dashboard has two Image.network sites, :312 and :1277, not just :1277.
  - the 27-sized / 12-unsized split is unverified; recount by hand.

3. FIREBASE STORAGE HAS NO CORS CONFIG
================================================================================

Blocked - needs production Firebase access, which we do not have.

Verified 2026-08-18 against a production Storage object: the file itself is
fine (HTTP 200, image/png, 177 KB), but the GET response carries NO
Access-Control-Allow-Origin header. The OPTIONS preflight answers "*", which is
firebasestorage's generic responder and does not help.

Flutter web runs CanvasKit, which must read the image's raw bytes to decode
them, so the browser enforces CORS and the load fails. A plain HTML <img> tag
would render the same URL fine - which is why pasting the URL into a browser
looks healthy. Android and iOS do not perform a CORS check and are unaffected.

Fix, once someone with project access can run it:

    cors.json:
    [{ "origin": ["http://localhost:*"], "method": ["GET"],
       "maxAgeSeconds": 3600 }]

    gsutil cors set cors.json gs://yoogeeapp.firebasestorage.app

Until then: test images on Android/iOS, or point web at the dev project
(picsum.photos, used by the seed, is CORS-clean).

4. SIGN-IN FAILS SILENTLY, NO LOADING UI, RAW ERROR MESSAGES
================================================================================

Full plan: docs/auth-signin-plan.md

Not Google-only. All six providers (Email, Google, Apple, GitHub, JWT,
Anonymous) route through _signInOrCreateAccount in
lib/auth/firebase_auth/firebase_auth_manager.dart:303, so they share one
try/catch and all the same defects.

The actual production bug: the release keystore SHA-1 is not registered on
yoogeeapp, so Google sign-in works on debug builds (dev project) and fails with
ApiException: 10 on release. Blocked on production Firebase access.

Everything else is why nobody could tell what was failing:

  - firebase_auth_manager.dart:315 catches only FirebaseAuthException. Google's
    failures arrive as PlatformException and are never caught.
  - firebase_auth_manager.dart:321 `e.message!` force-unwraps a nullable field,
    so a null message throws a SECOND exception inside the catch block. That is
    how email/password sign-in also fails silently. Same at :125 and :141.
  - The Google buttons are FlutterFlowIconButton, whose showLoadingIndicator
    defaults to FALSE. The email buttons are FFButtonWidget, which defaults to
    TRUE. Adding the argument at two call sites is the whole loading fix - no
    shared wrapper needed.
  - nav.dart:391 prepareAuthEvent() sets notifyOnAuthChange=false and only
    update() restores it, so a failed attempt leaves it stuck false.

Note for anyone working from older copies of this file: the claim that repeated
taps stack concurrent sign-in attempts is WRONG. Both button widgets guard
re-entry with `if (loading) return;` regardless of the flag.

5. onPostDeleted - NOW DEPLOYED. ORPHANED COMMENTS BACKLOG REMAINS
================================================================================

Found 2026-08-21 while checking what was live before the push deploy.
Full audit: docs/fcm-push-plan.md, "Production drift".

onPostDeleted was in the repo and in git history but NOT in
`firebase functions:list -P yoogeeapp`. The comment cascade had therefore never
run in production, and every post deleted since launch left its replies in the
`comments` collection. Clients cannot remove them - firestore.rules:53 is
`allow delete: if false` on comments, which is why the cascade is a function.

DEPLOYED 2026-08-21 to europe-west2, so posts deleted from now on cascade
correctly. THE BACKLOG IS UNTOUCHED and needs a one-off script: find comments
whose `postref` points at a document that no longer exists. Per the owner
(2026-08-21) the project is early enough in testing that no backfill is wanted.

Three gaps were found in the function itself. TWO ARE NOW FIXED (2026-08-21):

  - FIXED - the cascade was INCOMPLETE. Both `comments.postref` and
    `notifications.postref` point back at a post; only comments were deleted.
    A notification left pointing at a deleted post still rendered, and tapping
    it (notifications_widget.dart:381) navigated to RepliesWidget with a
    dangling reference - the same screen push tap-routing will use. Both
    collections are now queried in parallel and deleted through one chunk loop.
    A follow notification has no postref, so it correctly outlives the post.
  - retry was wired up, then TURNED BACK OFF by the owner before deploy
    (failurePolicy: false) pending cost monitoring. Deployed with retries off,
    so a failed cascade stays half-done permanently.
    WHY IT WAS A CONCERN: left unbounded, a v1 background function retries for
    SEVEN DAYS - backoff 10s, 30s, 70s, 150s, 310s, 630s then every 600s, so
    ~1,000 invocations for one stuck event, and stuck events retry
    independently. MAX_RETRY_AGE_MS (2 min) is still in the source and caps that
    at 3 retries whenever failurePolicy is flipped back to true. It is inert
    while retries are off, because the event age is always ~0.
  - STILL OPEN - the read is unbounded. .get() loads every matching document at
    256MB, now across two collections. The chunked commit anticipates volume;
    the read does not. Fine at current scale.
